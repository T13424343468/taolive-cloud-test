## 二、公开资料核验结论（影响方案的关键事实）

- 央视系官方直播流绑定 Referer 白名单、User-Agent 限制、IP 频控与动态 Token 鉴权，仅授权央视网、央视频 App 等自有渠道调用；第三方播放器硬编码地址会因缺合法 Referer、过期 Token 或未带加密签名被 CDN 拦截 403。
- CDN 对单 IP 的取流请求有频控：短时间高频请求 m3u8 会触发拦截规则。本轮日志里每 5 秒重试+热切起第二实例的请求密度，远超正常用户，不排除 403 有「频控自伤」成分——冷却降频后可能自愈，这正是观察期的依据之一。
- 部分流地址含时间戳/一次性密钥，有效期仅数秒至数分钟；持旧票重试必然被拒。
- 同类产品的通行做法不是硬闯单一源，而是多源家族兜底：持牌运营商源（如银河、百视通）、央视网(cntv)官方流、公开聚合清单（iptv-org 等，质量参差，仅作参考不内置）。
- 社区存在的「票据中转代理」（自建小服务代取接口换播放地址）属未授权聚合分发——道映红线不做。

## 三、逐项分析与对策

1. 问题2（403）：三种可能定性对应三种对策，摸底取证一次性判清——

   - 频控自伤 → 降速+观察期（G1、A），可解；
   - 真 IP 风控 → 客户端无解，只能等观察期到期或靠多源（G2）撑，如实提示。
2. 问题1（死循环）：自动跳台缺全局终局条件 → A 源级死判 + B 一圈封顶。
3. 问题3（热切）：403 不进热切，拉黑期禁第二实例 → C。
4. 问题4（取票口）：SSL 失败快断，不持旧票撞流，备用信息域名探测 → D。
5. 问题5：重连换路只治真网络级断流，与 403 分开记账 → E。
6. 问题6（白屏退出）：等内核最多约 2 秒，超时杀进程，启动自清理 → F。
7. 问题7（CCTV-7）：喂流断→快速判死→重连换路，判死阈值与 A 联动。

## 四、分层方案总纲

- 第一层·止血（v2 六项 A–F）：客户端行为收敛，死源快认输、不空转、说实话。
- 第二层·防自伤：
  - G1 请求纪律：所有重试/探测/热切的请求节奏压到频控线以下（阈值摸底取证后定稿）；拉黑观察期约 10 分钟，半开探测恢复。
  - G3 指纹对齐：起播请求与官方客户端逐头比对（Referer/UA/客户端标识），差异即修；摸底记录对比结论。
- 第三层·多源化（22:57 老板指令升级）：G2 摸底覆盖<strong>所有频道的所有源</strong>——可收台清单每个频道枚举其全部合法源（央视网 cntv 官方流、央视频、公开聚合中已验证可用的合法源等），同一套标准逐源探测、逐源记账；全部接入互相兜底：每频道按摸底健康度排成兜底链，一个源死→跳同频道下一源→跨源兜底，央视频不再是唯一支柱；用户自有源永远优先排最前。
- 第四层·用户兜底：提示如实（含「源暂时不可用」终局文案）、引导导入自有源；不动合规红线。
